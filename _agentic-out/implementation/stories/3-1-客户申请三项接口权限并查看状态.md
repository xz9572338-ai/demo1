# Story 3.1：客户申请三项接口权限并查看状态

Status: done

## Story

作为已通过入驻审核且已创建唯一应用的客户开发者，
我希望逐项申请客户基础信息、订单列表和订单详情三项查询接口权限并查看审核状态，
以便以最小权限完成业务对接。

## Acceptance Criteria

1. **固定权限目录与本企业应用**
   - **Given** `APPROVED` 客户已拥有 Story 2.1 创建的唯一 `ACTIVE` 应用
   - **When** 访问权限页或 `GET /console/api/v1/applications/{applicationId}/permissions`
   - **Then** 按固定顺序返回 `CUSTOMER_BASE_READ`、`ORDER_LIST_READ`、`ORDER_DETAIL_READ` 三项，每项包含名称、用途、数据范围、敏感提示和当前状态。
   - **And** 未申请项状态为 `NOT_APPLIED`；所有响应包含 `X-Request-ID`。
   - **And** 无应用或应用不属于当前企业时返回稳定 `404/403 ApiError`，不暴露其他企业是否存在该应用。

2. **逐接口提交与最小权限**
   - **Given** 某项权限为 `NOT_APPLIED` 或 `REJECTED`
   - **When** 客户选择该接口、填写 1–500 个 Unicode 码点的业务原因并提交
   - **Then** 平台仅为所选应用与接口创建独立 `PENDING_REVIEW` 申请，返回提交时间和 Request ID，未选接口不变。
   - **And** 驳回后重提创建新的申请记录，不覆盖旧原因；客户页只展示当前结果及当前可见驳回原因。
   - **And** 空原因、超长原因、未知接口代码或空选择返回 `400 VALIDATION_FAILED`，不写入部分记录。

3. **重复提交与并发边界**
   - **Given** 某项权限已为 `PENDING_REVIEW` 或 `APPROVED`
   - **When** 重复或并发提交该接口
   - **Then** 数据库唯一性/条件写入保证最多一个有效申请，其余请求返回 `409 PERMISSION_REQUEST_ALREADY_PENDING` 或 `409 PERMISSION_ALREADY_APPROVED`。
   - **And** 错误响应说明当前状态和下一步，不把冲突误报为 `500`。

4. **审核状态回填与客户可见结果**
   - **Given** 业务产品通过受控 SQL 对待审申请逐项批准或驳回
   - **When** 下一次读取权限页
   - **Then** 对应接口显示 `APPROVED` 或 `REJECTED`、更新时间及客户可理解的驳回原因；审批状态不做 Redis 缓存。
   - **And** 批准同时将该应用绑定到一个内部客户范围标识；只有三项封闭接口代码可被批准。
   - **And** 客户 API 不返回操作人、复核人、内部备注或内部客户范围标识。

5. **受控审核的完整性与失败关闭**
   - **Given** 受控审核脚本收到申请 ID、结果、客户可见原因、内部客户范围、操作人、复核人和审批时间
   - **When** 执行审核
   - **Then** 仅允许 `PENDING_REVIEW -> APPROVED|REJECTED`；驳回必须有原因，通过必须有客户范围，操作人与复核人规范化后必须不同。
   - **And** 申请更新、当前权限投影、客户范围绑定和审核记录在同一 MySQL 事务中提交；任一目标行数不是 1 或依赖失败时全部回滚。
   - **And** 非法终态再审、零行/多行、同人复核、缺失必填元数据均失败且不留部分状态。

6. **默认拒绝与跨企业隔离**
   - **Given** 权限为 `NOT_APPLIED`、`PENDING_REVIEW` 或 `REJECTED`
   - **When** 后续开放 API 安全入口查询应用的接口权限
   - **Then** permission 模块的公开应用层查询只对 `APPROVED` 返回允许，其余全部拒绝；本 Story 不提前实现 HMAC 入口。
   - **And** 使用企业 A 会话查询或提交企业 B 的 applicationId 始终被拒绝，且 B 的申请、状态、原因和绑定不变。

7. **页面反馈、键盘与错误恢复**
   - **Given** 客户只使用键盘
   - **When** 从应用页进入 `/permissions`，选择接口、填写原因并提交
   - **Then** Tab 顺序与 DOM 顺序一致，表单控件有程序化标签，Enter/Space 可完成主操作，字段错误与对应输入关联。
   - **And** 待审核、通过、驳回状态同时使用文字和语义样式，不仅依赖颜色；审核等待不显示虚假进度或预计时间。
   - **And** 加载/提交失败保留已有状态或用户输入，显示可理解原因、Request ID、重试操作和企业微信/邮件支持渠道。

8. **首发范围边界**
   - 本 Story 仅实现三项固定接口的申请、当前状态、受控人工审批和内部客户范围绑定。
   - 不实现运营审核 Web 后台、客户可见撤权历史、字段级审批、动态 API 目录、权限缓存、生产准入工作台、开放 API 签名或三个业务查询端点。

## Dev Notes

### 实现护栏

- 首发权限目录是代码/契约中的三项封闭枚举，不建通用 RBAC、角色树或运营配置平台。
- 首发已批准将原 Epic 3 的申请、当前状态、受控审批和内部范围绑定合并到本 Story；以 `epics.md` 顶部的“首发试点执行 Story”为权威范围。
- 客户控制台只读当前权限投影；审批历史保留于数据库供受控流程和内部审计，首发不向客户展示撤权历史。
- 当前权限判定必须可由 Story 5.1 通过 permission 模块公开应用层接口复用；不得让网关或 supplychain 跨模块查表。
- 审核和范围绑定与业务状态同事务，不引入 Redis 权限缓存，因此下一次读取立即观察新状态。
- 受控 SQL 模式必须吸取 Story 1.4 审核回填的行数分别校验和事务回滚经验，不用单个 multi-table `ROW_COUNT()` 伪造成功。
- 开放 API 权限验证在 Story 5.1 实现；本 Story 仅交付可复用的权威判定能力和默认拒绝语义，不扩张到 HMAC、nonce 或限流。

### 现有代码复用

- 会话主体与持续授权：`identity/application/AccountPrincipal.java`、`identity/infrastructure/SessionStatusRefreshFilter.java`。
- 单应用归属和状态：`application/application/ApplicationService.java`、`application/api/ApplicationController.java`。permission 模块不直接依赖 application Repository/表实现细节；若需跨模块能力，增加窄公开应用接口。
- 统一错误与请求标识：`shared/api/ApiError.java`、`shared/observability/RequestIdFilter.java`。
- 受控审核范本：`docs/runbooks/onboarding-review.sql`、`onboarding-review.md`。
- 前端路由和守卫：`apps/web/src/app/App.tsx`、`features/auth/SessionGuard.tsx`；应用数据访问和运行时校验模式：`features/applications/application-api.ts`。
- 当前前端尚未引入 TanStack Query/React Hook Form/shadcn 实现；为了保持首发节奏，沿用已有 React state/fetch/CSS 模式，不为本页单独引入新依赖。

### 技术与数据约束

- Java 21 + Spring Boot 4.1、React + TypeScript + Vite、MySQL 8.4 Testcontainers、Flyway、OpenAPI-first；不更换技术栈。
- 事务边界在 permission application 用例层；Controller 只做 DTO/身份映射，不实现审核规则或重试。
- 新约束必须使用 schema 级唯一名称；这与 MySQL 8.4 的 CHECK 约束命名规则一致。
- 审批写入使用 Spring/MySQL 事务与明确回滚条件；不在事务内调用外部 HTTP/Redis。
- 时间存储 UTC `DATETIME(6)`，API 返回带时区 ISO 8601；客户可见原因按 Unicode 码点计数。
