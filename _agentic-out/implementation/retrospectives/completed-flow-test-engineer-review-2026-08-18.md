# 已完成流程总结与 Agent 工具不足

日期：2026-08-18  
视角：测试工程师  
范围：只总结已经实际完成或已经执行过的流程，不讨论尚未开发的三个业务查询接口、正式上线和最终 UAT。

## 一、目前已经完成了哪些流程

### 1. 从业务想法整理成产品需求

项目最开始只有一个大致目标：给供应链合作客户提供开放 API，减少人工导出 Excel 和一对一定制开发。

Agent 通过多轮提问，逐步确认了：

- 第一批客户数量和应用数量。
- 一期只提供查询接口，不允许写生产数据。
- 入驻和权限申请由内部人员直接操作数据库审核。
- 在线调试只连接沙箱。
- 手机号、地址脱敏和境内数据处理要求。
- 一期明确不做运营后台、短信、Webhook、SDK、计费、多成员等功能。
- 上线成功指标和二期优先级。

随后生成并多轮验证了 Product Brief、PRD、成功指标、功能需求和非功能需求。

### 2. 完成架构和开发规划

已经确定了 Java/Spring Boot、React、MySQL、Redis、Flyway、OpenAPI 和 Testcontainers 等技术方案，并生成了：

- 系统架构设计。
- UX 和页面行为说明。
- Epic 与 Story 拆分。
- Sprint 状态文件。
- 项目开发规则和需求追踪规则。

期间还根据“第一期要更简单”的要求做过一次范围缩减。

### 3. 完成项目基础工程

已经建立前后端工程、数据库迁移、测试环境和基础质量检查，包括：

- Java 后端和 React 前端项目。
- MySQL、Redis 集成。
- Flyway 数据库版本管理。
- 后端单元测试、集成测试和 Testcontainers。
- 前端 Vitest 测试。
- OpenAPI 契约检查。
- ArchUnit 模块边界检查。

### 4. 完成账号和入驻流程

已经实现并测试：

- 企业客户注册和提交入驻申请。
- 人工审核入驻申请。
- 账号密码登录和退出。
- Redis 会话。
- 待审核、通过、驳回状态页面。
- 未通过客户不能绕过前端访问受限接口。
- 登录失败锁定、Cookie 安全属性和会话失效处理。

### 5. 完成应用和密钥流程

已经实现并测试：

- 每个客户创建一个应用。
- 生成 AppID 和 AppSecret。
- AppSecret 只显示一次。
- 页面离开前提醒客户保存密钥。
- 人工受控重置密钥。
- 重置操作的双人复核、幂等、并发和审计处理。

### 6. 完成接口权限申请流程

已经实现并测试：

- 客户申请三个查询接口的权限。
- 展示待审核、通过、驳回状态。
- 人工通过数据库脚本审核。
- 按接口保存客户数据范围。
- 默认拒绝、跨客户隔离和审核事务回滚。

### 7. 完成 API 文档和签名示例

已经实现并测试：

- OpenAPI 文档页面。
- 三个查询接口的参数和数据模型说明。
- 统一错误码。
- HMAC 签名规则。
- 固定签名测试向量。
- Java、Python、Shell 和 PowerShell 示例。
- API 文档登录保护、加载失败和重试。

### 8. 已经执行的质量流程

每个主要 Story 基本走过以下流程：

1. 创建 Story。
2. 开发实现。
3. 编写自动化测试。
4. 生成 automation 报告。
5. 生成需求追踪矩阵。
6. Blind Hunter 检查代码缺陷。
7. Edge Case Hunter 检查边界场景。
8. Acceptance Auditor 检查验收条件和证据。
9. 修复问题并重复评审。
10. 评审 Clean 后将 Story 标记完成。

目前 7 个 Story 已完成，开放 API 安全入口 Story 已完成开发和测试，但仍处于最终评审阶段，因此不把它算作完整闭环。

## 二、从测试工程师角度看，Agent 工具有哪些不足

## 1. 经常先写“测试通过”，再被评审发现其实没测全

这是最明显的问题。

例如登录 Story 的报告曾写 AC 已通过，但后续评审发现还没有测试：

- 未审核用户直接调用受限 API。
- Redis 创建、读取、删除会话失败。
- Cookie 的 `Secure` 和 `SameSite` 属性。
- 状态页面的 Tab 和 Enter 操作。
- 320/390 像素和 200% 缩放。

问题不在于最后没有补上，而在于报告过早写了 PASS。

对测试工程师的影响：测试报告不能直接相信，还要重新检查代码和测试内容。

应该改进：没有明确测试文件、测试名称、执行命令和结果的 AC，只能标记“未验证”，不能标记 PASS。

## 2. 喜欢用“测试数量”证明质量，但数量不代表场景覆盖

项目报告多次强调“通过 30 项、41 项、71 项、80 项测试”。这些数字有参考价值，但不能证明某个验收条件真的被测试。

例如有 71 项测试时，评审仍发现没有覆盖：

- 固定签名向量与服务端是否完全一致。
- Redis 各类失败结果。
- 限流一秒后是否正确恢复。
- 权限被拒绝时是否消耗 nonce 或限流额度。
- 不同权限使用不同客户范围时是否会串数据。

对测试工程师的影响：容易产生“测试很多，所以应该没问题”的错误安全感。

应该改进：报告以“场景覆盖表”为主，测试数量只放在附录。

## 3. 有些测试是在复制实现，不是在验证需求

这是比较危险的问题。

开放 API 签名测试曾使用与后端相同的完整路径算法生成签名，而正式文档和客户示例使用另一种路径。实现和测试写成同一种错误方式，所以测试仍然通过。

直到验收评审拿固定签名向量对比时，才发现客户按文档生成的签名无法通过服务端。

对测试工程师的影响：测试通过了，但客户实际调用仍可能失败。

应该改进：契约测试必须直接读取独立的 OpenAPI、固定测试向量或业务样例，不能在测试里重新写一份实现逻辑。

## 4. 有时用文本检查代替真正的功能测试

项目中曾用检查 CSS 文件里是否存在某些字符串，来证明页面支持窄屏和 200% 缩放；也曾用按钮 DOM 顺序来证明键盘可以完成操作。

这些只能证明“代码里写了样式或按钮”，不能证明用户真的能在浏览器里完成操作。

对测试工程师的影响：报告看起来覆盖了 UI 验收，实际上没有运行真实用户操作。

应该改进：页面布局、浏览器返回、Tab、Enter、缩放和剪贴板等行为，应使用浏览器级自动化测试或人工验收记录。

## 5. Story 开发前没有把测试条件问清楚

一些重要问题是在开发后才被发现：

- 状态页需要登录，但登录功能原来排在后一个 Story。
- “60 RPM + 突发 20”没有说清第几个请求开始拒绝、多久恢复。
- 签名时到底使用完整路径还是去掉环境前缀。
- 不同接口权限可以有不同客户范围，但上下文最初只有一个 scope。
- 失败请求是否消耗 nonce 和限流额度没有提前冻结。

对测试工程师的影响：无法提前设计确定的预期结果，只能等代码写完后再争论什么才算正确。

应该改进：Story 开发前必须做一次测试评审，至少明确输入边界、状态变化、错误码、并发、重试和失败副作用。

## 6. 自动化报告与真实代码状态容易不同步

项目里出现过：

- Story 正文是 review，frontmatter 还是 in-progress。
- Sprint 状态和 Story 状态不同。
- 报告写 38 项测试，实际已经是 41 或 42 项。
- 父任务打勾，下面的子任务没有打勾。
- 评审已经发现问题，traceability 仍显示 PASS。

对测试工程师的影响：无法快速判断当前版本到底能不能验收。

应该改进：Story 状态、测试结果和追踪矩阵应该由同一个命令统一更新，不能分别手工修改。

## 7. 故障测试经常补得比较晚

Agent 开始时更容易先覆盖正常流程，例如成功注册、成功登录、成功创建应用和成功申请权限。数据库故障、Redis 故障、事务中途失败、超时、重复请求和并发操作，往往由后续评审再补。

但这个项目是开放平台，真正容易出事故的恰好是这些失败路径。

对测试工程师的影响：正常流程很早就显示完成，高风险问题却在后期集中返工。

应该改进：涉及数据库、Redis、密钥和审核的 Story，在第一次测试设计时就必须包含依赖故障、重复请求和并发场景。

## 8. 多个评审 Agent 会重复报问题，也会出现误判

三个评审角色能够发现很多问题，这是优点。但同一个根因可能被不同 Agent 用不同说法重复提出；也出现过评审没有完全理解已经冻结的限流规则或执行顺序。

对测试工程师的影响：问题清单很长，但不等于每一条都需要独立修改。需要人工再次去重和确认。

应该改进：评审结果进入修复前，应自动按文件、AC 和根因合并，并标记“已确认、重复、误报、需要产品决定”。

## 9. 过多文档检查会挤占真实测试时间

项目建立了比较严格的 Requirement Change Log。它确实能防止需求变化没有记录，但也多次因为分类名称、追加方式或记录数量不一致而阻断 Story。

这些问题不会直接造成生产故障，却消耗了不少修复和复审时间。

对测试工程师的影响：容易把“文档格式正确”与“产品质量正确”混为一谈。

应该改进：初次实现记录和需求变更记录分开；普通实现不强制写变更日志，只有已批准行为发生变化时才记录。

## 10. 本地环境问题没有被工具提前发现

项目过程中遇到过：

- 本机一开始没有 Java 和 Docker。
- Maven 缓存目录在沙箱中不可直接使用。
- Testcontainers 需要 Docker 权限。
- 旧的编译或测试资源导致假失败。
- 生成 API 文档时意外修改了受版本控制的文件。

对测试工程师的影响：环境问题和产品缺陷混在一起，测试失败原因不清楚。

应该改进：开始开发或测试前，工具应自动检查 Java、Node、Docker、MySQL/Redis 测试能力、缓存权限和工作区是否干净。

## 11. 流程需要用户确认的次数太多

项目中出现了大量 `c`、`Y`、`0`、`A` 等单字符确认。很多只是继续执行下一步，没有提供新的业务信息。

对测试工程师的影响：测试过程被频繁打断，完整回归很难一次跑完。

应该改进：提供“批量执行到下一个阻断点”模式。只有范围变化、危险操作、真实验收失败或需要业务判断时才暂停。

## 12. 不同风险的功能使用了相近的测试强度

登录、AppSecret、签名和租户隔离值得严格测试；但普通状态展示、静态文档页面也经历了较多轮相同强度的审查。

对测试工程师的影响：时间没有优先花在最可能造成数据泄露或客户无法调用的地方。

应该改进：

- 低风险页面：基本功能测试和一次评审。
- 普通业务流程：正反向、数据库和权限测试。
- 高风险安全功能：边界、并发、故障注入、跨租户和多 Agent 评审。

## 三、测试工程师的总体评价

这个 Agent 工具的优点是愿意追问题到底，并且能通过多轮评审发现普通开发流程容易遗漏的安全问题。

它的不足不是“不会测试”，而是：

1. 测试结论有时写得太早。
2. 测试数量被看得太重，场景证据不够直接。
3. 有些测试跟着实现一起错。
4. 故障和边界测试加入得太晚。
5. 报告、Story 和 Sprint 状态容易不同步。
6. 多 Agent 评审缺少去重和误报管理。
7. 流程确认和文档维护过多，影响开发测试速度。

如果只做三项改进，优先顺序应该是：

1. **没有实际测试证据就不能标 PASS。**
2. **Story 开发前先由测试视角把边界、失败和并发规则问清楚。**
3. **所有状态和报告由测试执行结果自动生成，减少手工同步。**

做到这三点后，这套工具仍然可以保持严格质量，同时明显减少本项目中反复补测和重复评审的问题。
