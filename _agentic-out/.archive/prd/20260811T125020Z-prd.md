# 产品需求文档（PRD）— 轻量化开放平台

**作者：** user  
**日期：** 2026-08-11

## 执行摘要

轻量化开放平台面向现有供应链合作企业，为客户侧开发者提供标准化的 API 自助接入能力。平台将替代当前依赖微信、邮件传递 Excel 以及一对一定制接口的交付方式，解决数据获取实时性差、人工操作易错漏、重复开发成本高、接入流程不统一和调用问题难以定位等问题。

一期建设客户 Web 控制台及配套 API 开放能力。客户完成企业入驻审核后，可创建应用、获取 AppID 与 AppSecret、申请接口权限、查阅 API 文档、在沙箱环境在线调试，并查看应用近 7 天的调用统计。首期仅开放客户基础信息、订单列表和订单详情三个查询接口，不开放生产数据写入；入驻与接口权限审核暂由内部人员通过受控数据库操作完成。

平台采用 AppID + 请求签名鉴权，并对应用状态、接口权限、调用限流和客户数据隔离实施统一治理。沙箱与生产环境的凭证、数据、权限和访问地址相互隔离；生产调用需完成客户身份绑定和上线验收。首批面向 8～12 家存量合作企业，预计形成 8～15 个应用，原则上每家客户创建 1 个应用。项目首要目标是减少一对一定制开发及后续维护成本，其次是将客户从注册到首次调试连通的平均周期控制在 5 个工作日以内，并为后续客户和接口规模化扩展沉淀统一开放底座；一期不承诺替代全部历史定制接口。

### 产品差异化

本产品不定位为大而全的通用 API 管理平台，而是围绕存量供应链合作客户提供最短、最清晰的业务数据接入路径。其差异化来自对现有订单、客户资料、合作关系和内部流程的直接适配，以及用统一身份、应用凭证、接口授权、数据隔离和调用治理替代重复交付的执行效率。

核心洞察是：客户的数据需求具有高度重复性，问题根源不是缺少更多定制接口，而是缺少可复用、可管控的标准开放机制。平台从少量存量客户、三个高频只读接口和隔离沙箱开始验证价值，以较低业务风险跑通完整闭环，再根据真实采用情况渐进扩展。

## 项目分类

- **项目类型：** B2B API 平台，API 后端为核心并配套客户 Web 控制台
- **业务领域：** 供应链数据集成与开放平台
- **复杂度：** 中等
- **项目背景：** Greenfield

## 成功标准

### 用户成功

- 首批至少 5 家合作客户完成平台注册并创建应用。
- 客户从提交注册申请到首次在沙箱获得符合接口契约的成功响应，平均周期不超过 5 个工作日。
- 首次调试连通成功率不低于 80%；以进入正式调试的客户应用为分母，以首次接入周期内成功获得有效响应的应用为分子。
- 至少 6 个有效活跃应用；有效活跃定义为近 30 天存在排除内部测试后的生产成功调用。
- 客户可独立完成凭证获取、接口权限申请、文档查阅、沙箱调试和调用统计查看，不再依赖内部人员逐次讲解基础接入流程。

### 业务成功

- 一期指标在正式上线后的 3 个月观察期内完成验收。
- 与上线前基线相比，面向首批客户的人工 Excel 导出次数或相关处理工时下降至少 50%。
- 新客户不再默认采用一对一定制接口；三个标准接口能够覆盖首批客户的核心订单和基础资料查询场景。
- 建立人工导出次数与工时、定制接口平均交付工时、故障处理时长的上线前基线，并在验收期结束后量化平台带来的成本下降。
- 根据客户采用情况、接口申请量和数据库人工审核负担，为二期运营后台及接口扩充提供真实决策数据。

### 技术成功

- 生产 API 月度可用性不低于 99.9%；仅排除提前 3 个工作日通知且每月累计不超过 4 小时的计划维护窗口。
- 首发查询接口 P95 服务端响应时间不超过 1 秒，不含客户网络耗时；订单列表查询范围最大 31 天，单页最大 500 条。
- 平台自身原因导致的生产调用失败率不超过 1%，客户参数错误、鉴权失败、权限拒绝和主动限流不计入该指标。
- 客户、应用、AppID 与业务客户主数据必须正确绑定；跨客户数据访问测试零容忍，任何越权数据返回均阻断上线。
- 签名防重放、密钥保护、权限默认拒绝、审核审计、限流保护及生产与沙箱隔离全部通过上线验收。
- 调用日志可通过 Request ID 在内部检索，统计数据能够区分成功、鉴权失败、权限拒绝、限流、业务错误、超时和系统错误。

## 产品范围与分期基线

三个月内采用问题解决型 MVP，验证存量合作客户能否通过标准 API 安全、自助地获取分钟级供应链数据。首批按 8～12 家客户、8～15 个应用规划容量，原则上每客户 1 个应用，但平台能力不限制单客户只能创建一个应用。

| 能力域 | 核心 MVP（三个月上线） | 一期 1.x（三个月验收期内） | 二期及后续 |
|---|---|---|---|
| 账号与审核 | 企业注册、密码登录、状态及驳回原因；数据库受控审核 | — | 运营审核 Web 后台 |
| 应用与权限 | 应用、环境凭证、密钥轮换、停用、逐接口申请与生产验收 | — | 多成员与组织权限 |
| 开放接口 | 客户基础信息、订单列表、订单详情三个只读接口 | — | 扩充业务接口及版本管理 |
| 文档与调试 | OpenAPI 文档、签名示例、错误码、沙箱地址 | 页面沙箱在线调试 | SDK 与沙箱数据自助维护按需求评估 |
| 统计与诊断 | 近 7 天调用总量、成功/失败聚合、Request ID 内部检索 | 按接口筛选统计 | 异常告警、完整日志导出 |
| 安全治理 | 签名、防重放、权限默认拒绝、限流、客户隔离、审计、境内处理 | — | 根据规模增强治理能力 |

### 一期明确排除

- 运营审核 Web 后台、生产数据写入和连接生产环境的页面调试。
- 短信验证码登录、短信通知、自助找回密码和 Webhook 推送。
- 各语言 SDK 资源管理、多版本接口管理、计费、账单和流量套餐。
- 客户多成员、组织架构、调用明细日志导出和自动异常告警。
- 一期不承诺迁移或替代全部历史定制接口。

### 长期愿景

- 建设公司统一的外部能力开放入口，以标准接口逐步替代更多 Excel 交付和适合标准化的历史定制接口。
- 复用身份、凭证、授权、限流、隔离、审计和观测能力，降低新增客户与接口的边际成本。
- 根据真实采用和业务需求扩展供应链合作生态，不提前建设未经验证的通用平台能力。

## 用户旅程

### 旅程一：客户开发者完成首次生产接入

某长期合作企业的开发者李明过去每次需要订单数据，都要通过企业微信联系商务人员并等待 Excel。企业决定将数据同步到内部供应链系统后，李明进入开放平台注册企业账号，填写企业、联系人和手机号并提交入驻申请。

页面明确显示“待审核”，并告知审核渠道和预期处理方式。商务专员完成资质核验后，通过受控数据库操作将申请置为通过。李明登录平台创建应用，取得 AppID，并在仅首次展示页面复制和妥善保存 AppSecret。

李明分别申请客户基础信息、订单列表和订单详情权限。业务产品审核通过后，他按照统一文档实现签名，在沙箱中使用模拟数据调试。若签名失败，响应中的错误码、Request ID 和签名示例帮助他修正参数排序或时间戳问题。三个接口全部调通后，技术对接负责人核验客户身份绑定、接口权限和联调结果，批准生产上线并签发隔离的生产凭证。

首次生产调用成功是关键价值时刻：李明无需再次索要 Excel，也不需要我方为其开发专属接口。之后他可在控制台查看近 7 天调用量及成功、失败情况。

**揭示的能力：** 注册与审核状态、应用与密钥、权限申请、文档与签名示例、沙箱调试、生产验收、环境隔离、调用统计。

### 旅程二：客户开发者从接入失败中恢复

另一家客户的开发者王芳在沙箱调用订单列表时连续收到签名失败。她首先通过错误码确认失败发生在鉴权阶段，再使用 Request ID 与文档中的规范化签名示例核对请求。发现本地服务器时间偏差后，她修正时间同步并成功调用。

上线后，王芳因批量查询范围过大触发限流。平台返回 `429`、统一错误结构和 `Retry-After`，控制台统计将该调用归入限流失败。她根据文档缩小时间窗口、分页拉取并按建议退避重试，无需立即寻求人工支持。

若 AppSecret 遗失或疑似泄露，她可发起密钥重置。平台首次展示新密钥，新旧密钥并行 24 小时，之后旧密钥自动失效，客户也可提前终止旧密钥；重置操作形成审计记录。若仍无法解决，她通过企业微信或邮件提交应用、环境、时间和 Request ID，由技术对接负责人承接。

**揭示的能力：** 可诊断错误、时间偏差处理、限流与重试指引、密钥安全轮换、操作审计、人工支持升级路径。

### 旅程三：内部人员完成分工审核

客户提交入驻后，商务专员依据线下资质材料核验企业身份和合作关系。商务专员不直接任意修改业务表，而是使用受控脚本或存储过程，记录申请编号、审核结果、原因、操作人、复核人和时间。驳回时必须提供可供客户理解的原因，并遵循规定的重新申请状态流转。

客户申请接口权限后，业务产品根据合作范围和数据最小化原则逐接口审批，不能因企业已通过入驻而默认开放全部数据。生产上线前，技术对接负责人确认企业账号、应用、AppID 与内部客户主数据标识正确绑定，并验证沙箱联调结果、生产权限和限流配置。

三类审核均可追溯。任何身份绑定不明确、权限状态异常或审计信息缺失都会阻断生产启用。数据库审核虽然是一期临时方案，但必须维持与未来运营后台一致的合法状态机。

**揭示的能力：** 角色分工、最小权限数据库操作、受控状态流转、驳回原因、双人复核、完整审计、生产上线门禁。

### 旅程四：技术对接负责人协同运维处理生产故障

客户发现订单接口持续失败，通过企业微信或邮件反馈问题，并提供企业、应用、环境、发生时间、接口和 Request ID。技术对接负责人先检查账号、应用、权限、限流和错误分类；常见的签名、参数或权限问题直接向客户说明。

若问题涉及网关、日志或接口服务，技术对接负责人将完整上下文交给运维。运维通过 Request ID 检索内部日志，区分鉴权失败、权限拒绝、限流、业务错误、下游超时和平台 5xx，并确认是否影响其他客户。修复后，技术对接负责人通知客户验证，并记录原因、影响范围和处置结果。

即使一期不提供明细日志导出和自动异常告警，内部团队仍能依靠统一标识与错误分类建立最小可行的故障闭环，而不是重新回到无法定位的口头沟通。

**揭示的能力：** 标准问题受理信息、Request ID 全链路检索、错误分类、内部升级协作、影响范围判断、客户反馈闭环。

### 旅程五：产品与业务完成平台成效评估

上线前，产品负责人会同商务专员和技术对接负责人，按最近连续 3 个月记录首批客户的人工 Excel 导出次数与处理工时、一对一定制接口交付工时和故障处理时长，形成经三方确认的基线。上线后，产品负责人按月汇总注册客户、应用、权限申请、首次调通周期、生产活跃应用、人工审核工时和问题处置数据。

正式上线满 3 个月后，产品负责人组织商务、业务产品和技术对接负责人复盘，将实际结果与基线及成功标准逐项比较，形成一期验收结论和二期优先级建议。若人工数据库审核负担成为主要瓶颈，运营审核 Web 后台保持二期最高优先级；所有指标均保留数据来源、统计口径、责任人和复核记录。

该成效评估采用平台统计导出结果与内部人工台账完成，属于一期产品边界之外的运营程序，不新增运营后台或报表导出功能。

**揭示的能力：** 上线前基线、月度指标归集、三个月验收、跨角色复核、二期决策证据。

### 旅程需求汇总

- 客户必须随时看到入驻、接口权限和生产上线状态，以及驳回原因和下一步动作。
- 注册、应用、权限、客户主数据与环境必须形成可追踪的关联关系。
- AppSecret 必须仅首次展示，并支持安全轮换、旧密钥失效和审计。
- API 文档必须覆盖签名规范、错误码、分页、限流、重试及完整请求示例。
- 沙箱必须与生产保持接口契约一致，同时实现凭证和数据隔离。
- 生产上线必须有身份绑定、权限、联调、限流和审计门禁。
- 一期数据库审核必须采用受控操作、角色分工、合法状态机和可追溯记录。
- 所有调用必须生成 Request ID，并支持内部按应用、接口、环境、时间和错误类型检索。
- 客户支持流程必须明确受理信息、首接责任人、运维升级条件和结果反馈。
- 产品成效评估必须形成上线前连续 3 个月基线、上线后月度数据和三个月验收记录。

## 领域特定需求

### 合规与监管

- 平台仅在中国境内处理和存储数据，不设计跨境传输能力。
- 联系人手机号和收货地址属于个人信息，处理范围应限定在实现供应链查询目的所必需的最小范围，并明确访问用途和授权边界。参考[《个人信息保护法》](https://sdca.miit.gov.cn/zwgk/fgbz/art/2026/art_3e2ad39014b743d58bab7a6815640aee.html)。
- 项目应建立数据分类分级清单，至少区分账号信息、应用凭证、客户基础资料、订单数据、个人信息、调用日志和审计日志。参考[《数据安全法》](https://sdca.miit.gov.cn/zwgk/fgbz/art/2026/art_ce88eeb3d3744672a54923061c125885.html)。
- 尽管当前没有额外内部制度，平台仍须落实访问控制、安全认证、加密、备份和安全事件处置等基本数据保护措施。参考[《网络数据安全管理条例》](https://www.cac.gov.cn/2024-09/30/c_1729384452307680.htm)。
- 一期上线前由业务、安全或法务责任人确认三个接口的字段开放清单、处理目的、授权依据、留存期限和脱敏规则。

### 技术约束

- 手机号在控制台、沙箱示例、日志和接口响应中默认只展示前三位和后四位，中间字符使用掩码替代。
- 收货地址按最小必要原则仅展示省、市，区县、街道、门牌号和收件细节统一替换为 `***`。
- “展示脱敏”不替代安全存储：个人信息和 AppSecret 在存储、备份及传输过程中仍需采用适当的加密措施。
- 数据访问必须根据客户身份、应用、接口权限和内部客户主数据标识限定范围，跨客户数据返回为零容忍上线阻断项。
- 调用日志不得记录 AppSecret、完整签名、完整手机号或完整收货地址；排障日志同样遵循脱敏要求。
- 订单与客户数据需要达到分钟级可用时效；平台应监控数据中台同步延迟，并定义延迟超标时的错误或状态反馈。

### 集成要求

- 数据中台是客户基础资料和订单查询的权威数据来源；开放平台不得自行形成与数据中台冲突的业务事实副本。
- 订单列表应支持基于更新时间的增量查询、稳定排序和分页，使客户可以按分钟级节奏同步数据。
- 订单详情与列表中的标识、状态和更新时间必须保持一致；数据中台字段变更需经过接口契约兼容性评估。
- 沙箱模拟数据需要覆盖真实字段结构、枚举、脱敏结果、分页和错误场景，但不得复制真实个人信息或生产订单。
- 数据中台不可用或数据延迟超过阈值时，开放平台应返回可诊断错误，不得静默返回不完整或错误数据。

### 风险缓解

- **个人信息泄露：** 字段最小化、默认脱敏、存储与传输加密、日志避敏和访问审计。
- **跨客户数据泄露：** 强制客户标识绑定、服务与数据层双重校验、默认拒绝及自动化隔离测试。
- **数据时效不达标：** 监控数据中台更新时间、定义分钟级延迟阈值并提供异常处置机制。
- **数据契约不稳定：** 以 OpenAPI 和字段字典为统一来源，字段变更必须经过兼容性检查。
- **批量查询影响生产：** 限制时间范围和分页大小，实施应用与接口限流，并保护数据中台容量。
- **沙箱与生产不一致：** 对字段、签名、校验、分页和错误响应执行契约一致性测试。

## B2B API 平台特定需求

### 项目类型概述

平台以 REST API 为核心交付供应链客户与订单数据，并通过客户 Web 控制台提供入驻、应用、凭证、权限、文档、沙箱调试和调用统计能力。API 设计优先保证契约稳定、安全隔离、接入可诊断和分钟级增量同步，不承担生产数据写入。

### 技术架构约束

- 所有沙箱及生产 API 仅通过 HTTPS 提供服务。
- 沙箱与生产使用独立域名、AppID/AppSecret、权限和限流配置。
- API 网关负责请求签名、时间戳与 nonce 校验、应用状态、接口权限和限流；业务服务和数据访问层继续执行客户数据范围校验。
- 数据中台是客户与订单数据的权威来源；开放平台负责协议适配、安全治理和可观测性，不形成独立业务事实源。
- OpenAPI 是端点、参数、模型、示例、错误码和在线调试的统一契约来源。
- 每次调用生成全局唯一 Request ID，并贯穿网关、业务服务、数据中台访问和响应。

### API 端点规范

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/v1/customers/{customerId}` | 查询获授权客户的基础信息 |
| `GET` | `/v1/orders` | 按时间范围或更新时间增量查询订单列表 |
| `GET` | `/v1/orders/{orderId}` | 查询当前客户数据范围内的订单详情 |

- `customerId` 和 `orderId` 均不得直接决定数据可见范围；服务端必须结合已鉴权应用绑定的业务客户标识校验归属。
- 订单列表按 `updatedAt ASC, orderId ASC` 稳定排序，支持游标分页和更新时间增量查询；默认每页 100 条、最大 500 条，单次查询时间范围最大 31 天。
- 列表和详情中的订单标识、状态、更新时间与脱敏字段规则必须一致。
- 一期所有端点只读，不提供 `POST`、`PUT`、`PATCH` 或 `DELETE` 业务数据接口。

### 鉴权模型

- 签名算法采用 HMAC-SHA256。
- 每次请求携带 AppID、时间戳、nonce 和签名。
- 待签名内容覆盖 AppID、时间戳、nonce、HTTP 方法、路径、规范化查询参数和请求体摘要。
- 服务端允许客户端时间与服务器时间存在 ±5 分钟偏差；超出窗口的请求拒绝并返回明确错误码。
- nonce 在有效时间窗口内不得重复使用，防止请求重放。
- AppSecret 仅首次明文展示，服务端加密保存或使用密钥管理系统托管。
- 密钥重置后新密钥立即生效，旧密钥继续有效 24 小时；窗口结束后旧密钥自动失效，客户可在窗口内主动提前失效旧密钥。
- 应用停用、账号失效、权限未通过或环境不匹配时，所有请求默认拒绝。

### 数据与响应规范

- 请求与响应统一使用 UTF-8 编码的 JSON。
- 时间字段统一采用 ISO 8601 格式，并明确时区。
- 金额字段使用字符串形式的十进制定点数，不使用 JSON 浮点数表达。
- 通用响应结构包含 `code`、`message`、`requestId` 和 `data`。
- 列表响应的 `data` 中包含数据集合及分页信息。
- 手机号仅显示前三位和后四位；收货地址仅保留省、市，区县、街道、门牌号及收件细节统一替换为 `***`。
- 响应不得包含未经当前应用授权或不属于绑定客户的数据。

### 错误码要求

- 错误分类至少覆盖：参数错误、签名无效、时间戳过期、nonce 重复、应用不存在或停用、接口无权限、资源不属于当前客户、请求限流、数据中台超时、业务数据不存在和平台内部错误。
- HTTP 状态码与业务错误码保持一致语义；限流统一返回 `429`。
- 错误响应必须包含 `code`、`message` 和 `requestId`，不得暴露 AppSecret、签名原文、数据库结构或内部堆栈。
- 可恢复错误应提供明确处置提示，例如校准时间、检查权限、缩小查询范围或按 `Retry-After` 重试。

### 限流策略

- 默认按“应用 × 接口”限制为每分钟 60 次，并允许短时突发 20 次。
- 超限返回 `429` 和 `Retry-After`。
- 平台在数据中台入口达到 2,400 RPM 时启动保护，入口不得超过 3,000 RPM，并优先拒绝超出应用额度的请求。
- 客户额度调整须由业务产品批准并通过受控配置完成，审批、变更和失效信息均须审计。
- 限流属于系统保护机制，不作为严格计费或账单依据。

### API 文档要求

- 文档至少包含接口用途、环境地址、权限要求、参数、字段说明、脱敏规则、分页、增量查询、完整请求与响应示例、签名步骤、错误码、限流与重试建议。
- 签名章节必须提供规范化字符串示例，明确查询参数排序、URL 编码、空请求体摘要和大小写规则。
- 一期不提供各语言 SDK，但至少提供一种可直接复现的签名与调用示例。
- API 路径从一期起固定包含 `/v1`；一期不提供多版本管理界面或多版本并行治理能力。
- 在线调试从同一份 OpenAPI 契约生成，并且只能调用沙箱。

### 实施注意事项

- 在实现接口前，通过首批客户和历史 Excel 样本确认三个接口的字段覆盖率。
- 使用契约测试验证 OpenAPI、沙箱和生产接口的一致性。
- 对跨客户访问、签名篡改、nonce 重放、密钥轮换和限流执行专项自动化测试。
- 上线前完成数据中台分钟级时效与容量测试，并依据结果固化分页和查询范围上限。
- 关键安全、身份绑定、隔离、审计和下游保护能力不可作为进度压力下的降级项。

## 功能需求

### 账号与企业入驻

- **FR1：** 外部客户可以使用企业名称、联系人和手机号提交企业入驻申请。
- **FR2：** 平台可以为入驻申请维护待审核、通过和驳回状态。
- **FR3：** 外部客户可以查看当前入驻状态及驳回原因。
- **FR4：** 入驻被驳回的客户可以修改企业名称、联系人和手机号并重新提交；提交成功后申请由“驳回”转为“待审核”，已通过或待审核申请不得重复提交。
- **FR5：** 只有入驻审核通过的客户可以使用应用、权限申请、调试和统计功能。
- **FR6：** 外部客户可以使用账号和密码建立登录会话；退出后当前会话令牌立即失效，再次访问受保护页面必须重新认证。
- **FR7：** 同一账号 15 分钟内连续登录失败 5 次后锁定 30 分钟；同一 IP 15 分钟内失败 20 次后拒绝该 IP 新登录 30 分钟，人工密码重置可同时解除账号锁定。
- **FR8：** 内部责任人可以通过受控流程为客户执行人工密码重置。
- **FR9：** 商务专员可以记录入驻审核结果、原因和审核信息。

### 应用与凭证管理

- **FR10：** 审核通过的客户可以创建对接应用。
- **FR11：** 平台可以为每个应用生成唯一 AppID 和 AppSecret。
- **FR12：** 客户只能在 AppSecret 创建或重置后查看一次明文密钥。
- **FR13：** 客户可以查看本企业创建的应用及其状态。
- **FR14：** 客户可以自主停用应用。
- **FR15：** 客户可以重置应用密钥。
- **FR16：** 密钥重置后新密钥立即生效，旧密钥在 24 小时轮换窗口内继续有效；客户可提前终止窗口，窗口结束或提前终止后使用旧密钥的请求必须被拒绝。
- **FR17：** 客户不能访问其他企业的应用或凭证信息。
- **FR18：** 平台可以分别管理应用的沙箱凭证和生产凭证。

### 接口权限与生产准入

- **FR19：** 客户可以按应用查看可申请的开放接口清单。
- **FR20：** 客户可以为应用逐接口提交权限申请。
- **FR21：** 客户可以查看每项接口权限申请的待审核、通过或驳回状态及驳回原因。
- **FR22：** 业务产品可以记录接口权限审批结果、原因和审核信息。
- **FR23：** 平台只允许应用调用已获批准的接口。
- **FR24：** 应用停用后拒绝该应用全部环境调用；账号失效后拒绝其企业全部应用调用；接口权限撤销后拒绝该应用对该接口的新请求，状态变更须在 1 分钟内生效。
- **FR25：** 技术对接负责人可以记录客户身份绑定、联调结果和生产上线验收结论。
- **FR26：** 平台只为完成生产验收的应用启用生产访问。
- **FR27：** 平台可以维护企业账号、应用、凭证、接口权限与业务客户主数据标识之间的关联关系。

### API 目录、文档与调试

- **FR28：** 客户可以浏览客户基础信息、订单列表和订单详情接口的文档。
- **FR29：** 客户可以查看接口用途、访问地址、权限要求、请求参数、响应字段和示例。
- **FR30：** 客户可以查看签名规则、规范化请求示例、时间偏差和防重放要求。
- **FR31：** 客户可以查看分页、增量查询、限流、重试和错误码说明。
- **FR32：** 客户可以在页面向沙箱环境发起接口调试请求。
- **FR33：** 页面在线调试不能向生产环境发送请求。
- **FR34：** 文档、沙箱和生产接口的路径、参数、字段、校验、分页和错误语义必须与同一版本的 OpenAPI 契约一致，不一致项为 0。
- **FR35：** 客户可以取得至少一种可复现的签名和调用示例。

### 供应链数据查询

- **FR36：** 获得权限的应用可以查询当前绑定客户范围内的客户基础信息。
- **FR37：** 获得权限的应用可以按时间范围或更新时间增量查询当前客户的订单列表。
- **FR38：** 获得权限的应用可以按 `updatedAt ASC, orderId ASC` 使用游标分页遍历订单；后续页从上一页末游标之后读取，并发更新不得造成满足固定查询条件的订单永久遗漏或重复计入。
- **FR39：** 获得权限的应用可以查询当前客户范围内的订单详情。
- **FR40：** 平台可以拒绝查询不属于当前客户的数据资源。
- **FR41：** 平台以数据中台为客户和订单权威来源；订单列表与详情的 `orderId`、`customerId`、`status`、`orderAmount`、`createdAt`、`updatedAt` 及脱敏结果必须一致，允许的同步延迟不超过 5 分钟。
- **FR42：** 数据中台请求超过 3 秒、连接失败或数据延迟超过 5 分钟时，平台必须返回对应的 `DOWNSTREAM_TIMEOUT`、`DOWNSTREAM_UNAVAILABLE` 或 `DATA_STALE` 错误及 Request ID，不得以成功响应返回部分或过期结果。
- **FR43：** 对外响应中的手机号仅保留前三位和后四位；收货地址仅保留省、市，区县、街道、门牌号及收件细节替换为 `***`，适用于 Customer.contactMobile、OrderDetail.receiverMobile 和 OrderDetail.receiverAddress。
- **FR44：** 平台不向应用提供任何生产业务数据写入能力。

### 调用鉴权与流量治理

- **FR45：** 平台可以根据 AppID 和请求签名识别并验证调用应用。
- **FR46：** 平台可以拒绝签名无效、请求过期或重复使用防重放标识的请求。
- **FR47：** 平台可以同时校验账号、应用、环境和接口权限状态。
- **FR48：** 平台可以按应用和接口限制调用频率。
- **FR49：** 超过应用与接口额度时，平台必须返回 HTTP `429`、业务码 `RATE_LIMITED`、Request ID 和非负整数秒的 `Retry-After`。
- **FR50：** 经业务产品批准的客户额度调整必须记录客户、应用、接口、原额度、新额度、生效时间、失效时间、申请原因、操作人和复核人；未批准或过期配置不得生效。
- **FR51：** 单一应用持续达到其限流上限或产生突发流量时，其他客户仍须满足生产 API P95≤1 秒、月度可用性≥99.9%和平台原因失败率≤1%，且传递至数据中台的总流量不得超过 3,000 RPM。

### 调用统计与问题诊断

- **FR52：** 客户可以按应用查看近 7 天接口调用总量、成功数和失败数。
- **FR53：** 客户可以按接口筛选近 7 天调用统计。
- **FR54：** 平台可以区分鉴权失败、权限拒绝、限流、业务错误、超时和系统错误。
- **FR55：** 平台可以为每次接口调用生成唯一 Request ID。
- **FR56：** 技术对接负责人和运维可以根据 Request ID、应用、接口、环境和时间定位内部调用记录。
- **FR57：** 技术对接负责人可以记录客户问题、排查过程、处置结果和反馈状态。

### 数据保护与审计

- **FR58：** 平台可以按企业和业务客户标识隔离账号、应用、权限、调用记录和业务数据。
- **FR59：** 每次业务数据访问均必须校验资源所属客户是否在已鉴权应用的授权客户范围内；越权请求一律拒绝并产生审计记录，跨客户数据返回数为 0。
- **FR60：** API 访问日志、应用日志和错误日志不得记录 AppSecret、完整签名、完整手机号、完整收货地址或内部堆栈；手机号和地址如需记录必须使用 FR43 的脱敏结果。
- **FR61：** 平台必须记录入驻审批、权限审批、生产验收、密码人工重置、密钥重置、应用停用或启用、权限撤销和额度调整操作，不得以开放式类别替代上述审计范围。
- **FR62：** 审计记录可以标识操作对象、操作人、复核人、变更前后状态、原因和时间。
- **FR63：** 授权内部人员可以查询审计记录并追溯关键状态变更。
- **FR64：** 平台可以分别管理生产与沙箱的数据、访问权限和操作记录。
- **FR65：** 平台可以依据已批准的字段开放清单限制接口输出数据范围。

## 非功能需求

### 性能

- **NFR1：** 在 20 个生产应用、整体 3,000 RPM 且各接口每月有效样本不少于 1,000 的负载下，三个查询接口各自 P95 服务端响应时间不得超过 1 秒，不含客户网络耗时。
- **NFR2：** 在 50 个并发控制台会话下，登录、应用列表、权限状态和调用统计查询的 P95 服务端响应时间不得超过 2 秒；按每次发布后的验收记录判定。
- **NFR3：** 三个查询接口访问数据中台的单次超时为 3 秒；超时后 1 秒内须返回 `DOWNSTREAM_TIMEOUT` 和 Request ID，适用于沙箱及生产客户调用。
- **NFR4：** 订单列表单次查询时间范围不得超过 31 天，默认页大小为 100、最大为 500，并按 `updatedAt ASC, orderId ASC` 返回；超限请求必须返回参数错误且不访问数据中台。
- **NFR5：** 在 20 个并发应用各以每分钟 60 次请求、页面大小 500、查询范围 31 天运行 30 分钟时，系统仍须满足 NFR1、NFR7 和 NFR29。

### 可用性与可靠性

- **NFR6：** 生产 API 每自然月可用性不得低于 99.9%，按 `1-非计划不可用分钟/当月总分钟` 计算；仅排除提前 3 个工作日通知且每月累计不超过 4 小时的计划维护。
- **NFR7：** 每自然月平台 `5xx` 和平台超时请求数占进入平台的有效生产请求数不得超过 1%；客户参数、鉴权、权限和主动限流错误不计入分子或有效请求分母。
- **NFR8：** 核心服务发生故障后，恢复时间目标 RTO 不得超过 4 小时。
- **NFR9：** 核心平台数据的恢复点目标 RPO 不得超过 1 小时。
- **NFR10：** 单个应用以 5 倍默认额度持续请求 30 分钟时，其他客户仍须满足 P95≤1 秒、可用性≥99.9%折算目标及平台原因失败率≤1%。
- **NFR11：** 数据中台不可用或数据不完整时，平台不得将不完整结果伪装为成功响应。
- **NFR12：** 同一 API 版本下，沙箱和生产的字段、必填性、校验、签名、分页及错误语义与 OpenAPI 契约的不一致项必须为 0。

### 安全与隐私

- **NFR13：** 控制台、沙箱和生产 API 的所有网络通信必须使用 HTTPS。
- **NFR14：** AppSecret、手机号和收货地址在数据库、缓存持久化和备份中必须使用不低于 AES-256 强度的加密保护；密钥不得与密文存放于同一配置或数据存储中。
- **NFR15：** AppSecret、完整签名、完整手机号、完整收货地址和内部错误堆栈不得写入 API 访问日志、应用日志或错误日志。
- **NFR16：** 手机号在对外响应和展示中仅保留前三位和后四位；收货地址仅保留省、市，其他地址信息统一替换为 `***`，适用字段以 v1 数据契约为封闭清单。
- **NFR17：** 客户数据访问必须同时通过应用身份、接口权限和业务客户归属校验。
- **NFR18：** 任意访问非授权客户资源的请求必须被拒绝并记录客户、应用、资源、时间和 Request ID；跨客户数据返回事件必须为 0。
- **NFR19：** 请求签名必须具备时间窗口和防重放保护；重复 nonce 和过期请求必须被拒绝。
- **NFR20：** 密钥明文只能在创建或重置时展示一次，之后任何用户和普通运维人员均不能直接查看。
- **NFR21：** 登录锁定、审核、人工密码重置、密钥重置、应用状态、权限、生产启用和限流调整必须记录操作对象、操作人、复核人、前后状态、原因、时间和 Request ID（适用时），必填字段完整率为 100%。
- **NFR22：** 平台仅在中国境内处理和存储业务数据，不得向境外系统传输。
- **NFR23：** 产品负责人、业务产品和技术对接负责人须在生产启用前共同批准数据分类分级、字段开放清单、个人信息处理目的和留存规则；批准记录及版本号是生产启用的必备证据。

### 容量与扩展性

- **NFR24：** 一期平台必须支持至少 20 个同时启用且各自可按默认 60 RPM 额度调用的生产应用。
- **NFR25：** 平台必须支持整体每分钟至少 3,000 次 API 请求，并在该负载下继续满足性能和失败率指标。
- **NFR26：** 当传递至数据中台的总请求达到 2,400 RPM（一期 3,000 RPM 容量的 80%）时，平台必须先对超出应用额度的请求返回 `429`；数据中台入口流量不得超过 3,000 RPM。
- **NFR27：** 新增只读查询接口不得引入第二套账号、凭证、权限、限流、隔离、审计或统计模型；上述七类公共能力的复用覆盖率必须为 100%。
- **NFR28：** 应用与接口维度的限流额度必须可独立调整，且调整过程不得要求中断其他客户服务。

### 数据时效与集成质量

- **NFR29：** 数据从数据中台可用到开放 API 可查询的延迟 P95 不得超过 5 分钟。
- **NFR30：** 平台须每分钟监测数据中台失败率、P95 耗时和数据延迟；指标异常后 2 分钟内在内部监控中标明数据中台或平台来源，覆盖三个开放接口。
- **NFR31：** 每日抽取不少于 100 个订单（不足时全量）比对列表和详情的 `orderId`、`customerId`、`status`、`orderAmount`、`createdAt`、`updatedAt` 及脱敏结果，不一致率必须为 0。
- **NFR32：** 增量查询在相同排序条件下不得因分页过程造成符合条件的数据永久遗漏。
- **NFR33：** 数据中台字段或枚举变化不得删除 v1 必填字段、改变既有字段类型或改变既有枚举语义；不兼容变化必须通过新的 API 主版本提供。

### 日志、审计与可观测性

- **NFR34：** 每次 API 调用必须具有全链路唯一 Request ID。
- **NFR35：** 调用日志必须支持按 Request ID、应用、接口、环境、时间和错误分类检索。
- **NFR36：** 用于问题排查的调用日志至少保留 90 天。
- **NFR37：** FR61 所列全部操作的审计日志自发生时间起至少保留 1 年，并在保留期内可按操作对象、操作人和时间检索。
- **NFR38：** 调用统计采用中国标准时间（UTC+8）自然日，每小时刷新一次，调用发生至控制台可见的延迟不得超过 2 小时；HTTP `2xx` 且业务码成功计为成功，其余终态请求计为失败，同一 Request ID 仅计一次。
- **NFR39：** 日志和监控组件故障不得绕过鉴权、授权或数据隔离控制。

### Web 兼容性

- **NFR40：** 客户 Web 控制台必须支持 Chrome 和 Edge 最新两个主要版本。
- **NFR41：** 一期不要求移动端优先、搜索引擎优化或旧版浏览器兼容。
- **NFR42：** 注册、登录、创建应用、复制首次密钥、提交权限申请、查看文档、发起沙箱调试、重置密钥和查看统计九项流程必须仅用键盘完成；所有输入有程序化标签，状态与错误同时提供文本名称、原因和下一步动作，不得仅靠颜色表达。
