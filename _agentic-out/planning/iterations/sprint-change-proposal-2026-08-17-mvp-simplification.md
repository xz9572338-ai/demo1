# Sprint Change Proposal：一期首发试点瘦身

## 1. 变更原因

当前一期规划包含 6 个 Epic、41 个 Story，以及凭证双环境生命周期、24 小时轮换、逐接口审批全流程、生产准入清单、在线调试、调用统计、不可变审计、异步统计、精细容量保护和完整异常矩阵。Story 1.3 的实施与评审已经表明，即使单个登录能力也会扩展为大量契约、故障注入、追踪和验收工作，按现有范围继续推进难以满足“快速落地”的原始业务目标。

本次变更不是降低客户数据隔离、签名鉴权或只读边界，而是把一期拆成“首发试点”和“增强版 1.x”：首发试点只交付首批客户完成三项查询接口调用所必需的最短闭环，其余能力延期，不返工已完成成果。

## 2. 变更原则

1. 保留 Story 1.1～1.3 已完成或已进入评审的注册、登录和工程底座，不回滚。
2. 保留不可妥协的安全底线：只读接口、AppID + HMAC 签名、时间戳与 nonce、防重放、应用状态与权限校验、客户数据隔离、手机号及地址脱敏、Request ID。
3. 首发试点采用人工审核、人工生产开通和固定配置，暂不建设可视化运营与高级自助治理。
4. 优先复用现有框架和简单同步流程，暂不引入为未来规模预建的异步统计、复杂缓存、动态配额和高级审计查询。
5. 首发试点以 8～15 个应用的小规模客户验证为边界；达到真实使用后，再按数据决定增强版 1.x 的投入顺序。

## 3. 推荐范围基线

### 3.1 首发试点保留

| 能力域 | 首发试点交付内容 |
|---|---|
| 账号与入驻 | 企业注册、账号密码登录/退出、待审核/通过/驳回状态查看；内部人员直接更新数据库审核结果 |
| 应用与凭证 | 每客户最多 1 个应用；创建后生成 AppID/AppSecret；密钥仅首次显示；忘记或泄露时由技术人员人工重置 |
| 接口权限 | 客户勾选三项查询接口并提交；页面显示待审核/通过/驳回；业务产品通过数据库回填结果 |
| API 文档 | 静态 OpenAPI 文档、统一错误码、签名说明，以及 cURL、Java、Python 固定示例 |
| 网关安全 | AppID + HMAC-SHA256、时间戳与 nonce、应用状态、接口权限、客户归属、固定每应用 60 次/分钟限流 |
| 查询接口 | 客户基础信息、订单列表、订单详情三个只读接口；订单列表使用简单 `page/pageSize` 分页 |
| 环境与上线 | 固定沙箱数据；技术负责人按线下清单验收后人工开通生产凭证；页面不提供生产调试 |
| 运维诊断 | 结构化调用日志、业务错误码和 Request ID；客户通过企业微信/邮件反馈，技术负责人按日志排查 |

### 3.2 延期到增强版 1.x

- 驳回后在线修改资料和重新提交；一期首发由商务线下沟通并人工处理。
- 应用自主停用/恢复、24 小时双密钥轮换、提前失效以及完整凭证状态面板。
- 独立的沙箱/生产凭证自助生命周期页面；首发由人工生产开通替代。
- 权限撤销历史、字段级开放审批、特殊客户动态配额和生产准入工作台。
- 自研 API 文档工作台、页面在线调试器、响应诊断器。
- 客户调用统计页面、按接口筛选、异步事件/Outbox、统计聚合与问题工单模块。
- 内部审计查询页面、不可变审计浏览能力和完整运营报表。
- 游标增量同步、复杂并发分页语义、下游精细容量隔离和高规模性能门禁。
- 全量 WCAG AA 状态矩阵、全部窄屏场景和视觉回归；首发只保证注册、登录、状态、应用、权限、文档五个核心页面的键盘可用与常用桌面尺寸。

### 3.3 继续排除

运营审核 Web 后台、生产写入、生产环境在线调试、短信、找回密码、Webhook、SDK 管理、多版本、计费、客户多成员和调用明细导出继续不在一期范围内。

## 4. Story 重组方案

Story 1.1～1.3 保留现状。剩余首发工作合并为 8 个 Story；原未实施 Story 不删除，统一移至 1.x Backlog，并在 Epic 文档中保留来源映射。

| 新执行顺序 | 首发 Story | 合并或替代的原范围 |
|---|---|---|
| 1 | Story 1.4：查看入驻状态与人工审核结果 | 原 1.4 的状态查看；资料在线修正延期；原 1.5 简化为数据库审核说明 |
| 2 | Story 2.1：创建单一应用并首次领取沙箱密钥 | 原 2.1、2.2 的最小部分；每客户仅 1 个应用 |
| 3 | Story 3.1：申请三项接口权限并查看审核状态 | 原 3.1～3.4 的最小闭环；数据库审批并绑定客户范围 |
| 4 | Story 4.1：发布 OpenAPI 文档和固定签名示例 | 原 4.1～4.3 合并；不建设自研调试工作台 |
| 5 | Story 5.1：实现签名鉴权、权限、租户隔离与固定限流 | 原 1.6、5.1、5.7 的安全核心 |
| 6 | Story 5.2：交付三个只读查询接口 | 原 5.2～5.6 合并；简单分页、脱敏、统一错误 |
| 7 | Story 5.3：沙箱联调与人工生产开通 | 原 3.6、5.10、5.11 的轻量替代 |
| 8 | Story 5.4：首批客户端到端验收与部署 | 覆盖核心安全、契约、桌面 Web 和部署冒烟 |

首发不再单独实施 Epic 6；Request ID 和基础调用日志作为 Story 5.1/5.2 的验收项交付。

## 5. 工件影响与拟修改内容

### PRD

- 新增“首发试点基线”，明确其优先于原一期完整范围。
- 将成功标准聚焦为：至少 5 家注册、至少 3 家完成首次生产调用、平均接入周期不超过 5 个工作日、跨客户数据泄露为 0。
- 将调用统计、密钥轮换、自主停用、在线修改重提、高级生产准入和精细容量指标移至 1.x。
- 将性能门槛调整为适合 8～15 个应用的试点容量：聚合 300 RPM、单接口 P95 不超过 2 秒（不含数据中台明确超时），不再以 3000 RPM 和月度 99.9% 作为首发阻断项。

### Epics 与 Sprint

- 保留 Story 1.1～1.3 的状态和证据。
- 将剩余首发工作重排为上述 8 个 Story。
- 原复杂 Story 标记为 1.x Backlog，不再阻塞首发完成。
- Sprint 当前主线从“完成全部 Epic 1”切换为“先完成 Story 1.4，再贯通应用—权限—文档—API—生产试点”。

### Architecture

- 保留 Java/Spring Boot、React、MySQL、Redis 和 OpenAPI-first。
- 首发采用模块化单体与同步处理；取消首发 Outbox/统计聚合模块、问题工单模块、动态配额审批、内部审计查询。
- 密钥首发使用单一凭证模型和受控加密配置；KMS 信封加密及 24 小时双密钥轮换移至 1.x。
- Redis 仅用于登录会话、登录防护、nonce 和固定限流，不为未交付能力预建缓存。
- 部署仍区分沙箱与生产配置，但生产凭证与启用由技术负责人线下执行。

### UX

- 首发控制台缩减为注册、登录/入驻状态、应用与凭证、接口权限、API 文档五类页面。
- 移除首发总览六阶段看板、复杂应用工作区页签、轮换面板、沙箱调试器、统计图表、生产准入工作台和问题工单交互。
- 保留状态文字、错误码、Request ID、键盘操作和桌面响应式基本要求；完整移动端与全部状态视觉回归移至 1.x。

### 测试

- 每个首发 Story 保留关键单元/集成测试，不再要求为延期能力建立测试脚手架。
- 建立 1 条客户注册登录到生产查询的核心 E2E，以及签名失败、无权限、跨客户访问、限流四条安全路径。
- Redis、MySQL、数据中台只覆盖首发实际调用链的失败关闭；不开展未上线模块的故障矩阵。

## 6. 方案评估

### 推荐方案：首发试点瘦身，无回滚

- **收益：** 复用已有成果，最大限度减少剩余 UI、状态机、异步统计、复杂治理与测试工作；可以更早让客户产生真实调用。
- **代价：** 首发阶段更多依赖数据库操作和人工技术支持；客户自助能力、可观测性和凭证运维体验较弱。
- **风险控制：** 所有人工操作使用受控 SQL/操作清单并留执行记录；安全底线与数据隔离不延期；首批规模限制在 8～15 个应用。

### 不推荐：维持现有完整一期

范围最完整，但无法解决当前交付速度问题，且会在尚未取得真实客户使用证据前投入大量增强能力。

### 不推荐：回滚已完成登录与安全能力

不能显著减少后续主链工作，反而引入返工和身份安全风险。

## 7. 预计影响

- 剩余首发 Story：由约 31 个缩减为 8 个。
- 预计首发开发周期：在人员可用、数据中台接口稳定的前提下约 4～6 周；这是规划估算，不是承诺日期。
- 功能削减：约 60%～70% 的剩余自助治理、统计和增强体验延期。
- 已完成代码：全部保留，不做破坏性回退。
- 文档变更规模：Substantial，涉及 PRD、Epics、Sprint、Architecture、UX、Story 导航与追踪矩阵。

## 8. 实施顺序与验收

获得批准后按以下顺序批量执行：

1. 更新 PRD 的首发/1.x 范围和成功标准。
2. 重组 Epics、Story 映射和 Sprint 状态，保留历史证据。
3. 增加架构“首发实施剖面”，删除首发不需要的强制依赖。
4. 收缩 DESIGN/EXPERIENCE 与 UX 说明中的首发页面和状态。
5. 更新追踪矩阵、实施就绪信息和下一 Story 指向。
6. 对全部权威工件执行术语、编号、范围与状态一致性检查。

验收条件：任一首发需求都能追踪至 8 个剩余 Story 之一；任一延期能力均明确标记 1.x；Story 1.1～1.3 的已交付行为不丢失；安全与客户数据隔离要求无降级。
